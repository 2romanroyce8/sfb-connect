# Runbook — Client portal (/portal) and agency Clients tab (/app/clients)
- Tables (applied 2026-10-27, additive): agy_client_members, agy_client_invites, agy_onboarding; helper agy_is_client_member(). RLS + least-privilege grants. Access tested in a rolled-back transaction: a client user sees only their own client and onboarding, can save their own draft, cannot approve themselves, cannot touch another client's onboarding, cannot add themselves to a client, sees no leads; anon sees nothing.
- Flow: agency adds a client (/app/clients) → "Create link" for the client's email (single-use, 7 days, only that email; only the token's SHA-256 is stored; nothing is emailed by us) → client opens /portal/join?token=…, signs up or signs in with THAT email → server accepts (service client) → /portal shows their onboarding → client saves / submits → agency approves or requests changes (a note is required) → approving marks the client Active.
- Client portal pages: /portal (status + progress), /portal/onboarding (form from lib/agency/onboarding.ts, the single definition used by the form, the API and the agency view). Notes warn against passwords; credential-looking text blocks the Submit button client-side.
- Security: client id is never read from the request (looked up from membership); writes use the session client so RLS decides; invite accept is rate-limited and the single-use claim is atomic; portal pages are noindex.
- Not built yet: files, tasks, appointments, billing and support inside the portal (the overview says so), portal email notifications, reminders, a client-removal button.
